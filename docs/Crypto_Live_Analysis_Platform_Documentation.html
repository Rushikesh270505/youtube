Crypto Live Analysis Platform Documentation

Single-document overview of the platform, how crypto live analysis works in the system, the technology stack, the voice-pack system, and the conversation-generation pipeline. Prepared on April 9, 2026.

Purpose: This document explains the platform as a whole. It covers the live crypto analysis workflow, the frontend and backend architecture, the tech stack, how voice packs are used, and how spoken multi-speaker conversations are generated.

1. What This Platform Is

This is a crypto live analysis platform designed for live market monitoring, visual analysis, commentary generation, and trading education. It combines:

  • a live chart and pattern-detection overlay
  • a strategy lab / backtest experience
  • a voice commentary layer
  • a podcast-style multi-speaker conversation engine
  • desktop packaging for local app distribution

The platform is designed to feel like a professional live trading and commentary desk, but it is primarily a simulation and analysis environment rather than a real brokerage execution system.

2. What Crypto Live Analysis Means In This Platform

Crypto live analysis means reading the market while price is actively moving and presenting that read in a usable form. Instead of relying only on static charts, the platform combines:

  • live Binance price and candle data
  • pattern and structure analysis across multiple timeframes
  • contextual summaries
  • headline integration
  • voice and subtitle delivery

The platform is not only trying to answer “what is price doing?” It is also trying to answer:

  • what structure is dominant
  • how confident the read is
  • which timeframe is leading
  • whether the market is transitioning or confirming
  • how to explain that read clearly to a viewer or listener

5. Core Runtime Architecture

The platform works in layers.

5.1 Frontend Layer

The main overlay frontend is loaded from static files. It renders:

  • the live chart
  • the active coin rotation
  • pattern summaries
  • headline feed
  • voice status and playback controls
  • subtitle output from spoken commentary

5.2 Backend Layer

The backend exposes a unified local API. It serves:

  • voice status APIs
  • voice assignment APIs
  • commentary rendering APIs
  • podcast rendering APIs
  • strategy lab APIs
  • audio file endpoints for generated clips

5.3 Voice Layer

The voice layer decides which voice engine to use, synthesizes clips, caches them, and exposes them back to the UI.

6. How The Live Analysis Works

Step 1: Market Data Is Collected

The live overlay reads Binance market data using REST and WebSocket sources. The main overlay rotates through coins such as:

  • BTC
  • ETH
  • SOL
  • XRP
  • DOGE
  • PEPE
  • PAXG

Step 2: Multi-Timeframe Analysis Is Built

The analysis layer works top down, using intervals such as:

  • 4H
  • 1H
  • 30M
  • 15M
  • 5M
  • 1M

These intervals are used to build alignment, identify leading structure, and determine whether lower timeframe moves agree with higher timeframe context.

Step 3: Patterns And Structure Are Summarized

The detector and intermission utilities generate structured reads that describe:

  • dominant pattern or regime
  • bias
  • confidence
  • alignment across timeframes
  • support and resistance context
  • headline-aware narrative transitions

Step 4: Visual Output Is Updated

The frontend updates:

  • price chart
  • pattern card
  • news panel
  • rotation timer
  • voice subtitle layer
  • intermission overlay

Step 5: Spoken Commentary Can Be Generated

When commentary is enabled, the backend converts the current market read into structured speaking turns and then renders those turns as audio clips.

7. How System Voice Packs Are Used

7.1 Voice Pack Configuration

The platform uses voice-pack definitions stored in:

  • voice_packs/hosts.json

Each voice pack defines:

  • an internal pack id
  • display name
  • role
  • podcast role
  • engine type
  • model path
  • pause length
  • subtitle color
  • fallback system voice
  • Google voice metadata for Gemini audio

7.2 Current Default Packs

The default manifest currently uses three packs:

  • neutral_analyst
  • high_energy_host
  • calm_educator

7.3 Runtime Selection

The system does not always use only one voice engine. Instead, it resolves the best available runtime for each pack. The runtime-selection logic supports:

  • Gemini Live / Gemini TTS: preferred when configured and available
  • Piper: preferred local model runtime when a model is available
  • macOS say: system-voice fallback on macOS
  • None: subtitle-only mode if no runtime is available

This means the platform can keep working even if a preferred voice model is missing.

7.4 Why System Voices Matter

System voices are important because they make the platform usable immediately on a macOS machine without waiting for custom local TTS models. If custom Piper or Gemini-backed voices are not ready yet, the app can still speak using local system voices through say.

7.5 Voice Assignment Layer

The app also supports persistent voice-role assignments. A user can map roles like:

  • Analyst 1
  • Analyst 2
  • Host

to selected voices using the voice-assignment API. Those assignments are stored locally so the voice cast remains stable across sessions.

8. How The Platform Builds Conversations

8.1 Commentary Modes

The short-form commentary system supports multiple modes, including:

  • intermission summary
  • intermission news
  • subscribe call-to-action
  • live event reactions

These modes are planned in the commentary service and each one builds a sequence of speaking turns.

8.2 Conversation Planning

The short commentary pipeline works like this:

  1. The frontend or another part of the app sends a commentary request.
  2. The backend chooses a commentary mode.
  3. The service builds a list of clips in speaking order.
  4. Each clip is assigned a speaker, text, pause length, and stage.
  5. The clips are rendered into audio or returned as subtitle-only data.

8.3 Multi-Speaker Podcast Conversations

The richer conversation system is handled by the podcast engine. It creates a structured roundtable using roles like:

  • Analyst 1
  • Analyst 2
  • Host / Narrator

The engine takes live context, timeframe analyses, and headline data, then turns them into a script package.

8.4 What The Podcast Engine Produces

The podcast render pipeline produces:

  • a structured multi-speaker script
  • plain text transcript
  • speaker metadata
  • per-clip audio files
  • timestamped transcript entries
  • a merged audio file when possible

8.5 Why Conversations Sound Structured

Conversations are not random text blobs. They are assembled from role-based templates and seeded phrase variations. That gives the output:

  • clear speaker turns
  • consistent speaking roles
  • controlled pacing
  • repeatable style
  • market-aware transitions

The result is a format that feels more like a live analyst desk than a single robotic narrator.

10. Stream Controls And Audio UX

For a live crypto analysis platform, audio controls are part of the operator workflow, not just a cosmetic option. The platform should keep voice and BGM controls available even during the stream-start countdown or starting timer.

10.1 Why Voice And BGM Sliders Matter

  • The operator may need to balance commentary loudness before the stream fully opens.
  • BGM often needs to be reduced before spoken analysis starts.
  • Countdown periods are commonly used to test the final live mix.
  • Hiding audio controls during the start timer creates unnecessary friction right before going live.

10.2 Recommended Behavior

During the starting timer / countdown phase, the interface should still allow:

  • voice volume adjustment
  • background music volume adjustment
  • voice enable / disable toggle
  • BGM selection or mute control
  • final pre-live sound check without leaving the main overlay

10.3 How It Fits Into The Existing Platform

The current platform already has:

  • voice commentary APIs
  • voice-assignment APIs
  • BGM playlist APIs
  • a visible rotation / countdown timer in the live overlay

Because those systems already exist, keeping voice and BGM sliders visible during the starting timer is a natural extension of the current architecture.

10.4 Product Recommendation

From a UX point of view, the cleanest design is:

  1. show the stream-start timer prominently
  2. keep voice and BGM sliders pinned in the top bar or control dock
  3. allow changes while the countdown is active
  4. preserve the selected levels when the stream transitions into live commentary mode

11. Packaging And Distribution Stack

The project is also packaged as a desktop app.

  • Electron provides the desktop shell.
  • electron-builder builds the distributable app.
  • PyInstaller bundles the Python backend into a desktop-friendly backend executable.

12. Why This Architecture Works Well

  • The live analysis layer is separated from the voice layer.
  • The voice system can fall back safely if a preferred runtime is missing.
  • The conversation engine can reuse the same market inputs in both short-form and long-form commentary.
  • The backend API keeps voice, analysis, strategy, and file serving in one local service.
  • The desktop packaging stack makes the whole system easier to run as one app.

13. Final Summary

This platform performs crypto live analysis by collecting live market data, analyzing structure across multiple timeframes, and then presenting that analysis visually and verbally.

Its major strengths are:

  • live market analysis
  • pattern and structure visualization
  • voice-pack based commentary
  • multi-speaker conversation generation
  • desktop-ready packaging

In simple terms, the system works like this:

  1. get live market data
  2. analyze it
  3. summarize it
  4. render it on screen
  5. optionally turn it into spoken commentary using voice packs and structured conversation templates
